# 当前数据产品、开发职责与来源追溯

更新日期：2026-10-01。依据本次用户说明、当前代码、实际源文件和 `mag_v3` 交付包整理。

## 1. 当前阶段的目标

团队目前从一篇论文涉及的样本中取得了一部分测序数据，用这批样本跑通生信流程，并基于交付结果开发查询、统计与可视化。之后计划在大服务器上批量运行生信流程，接入更大范围的数据。

当前工作的目标是形成可以重复使用的“样本选择 → 生信分析 → 数据交付 → 校验入库 → 可视化分析”链路。此说明按这次讨论的生信与可视化范围编写。

已通过 NGDC 官方导出逐条确认当前 185 个 Run 属于 CRA014435/PRJCA022804，正好是官方全部 AD 122 个和 NC 63 个；完整项目有 476 个样本。2025 年来源论文 DOI 为 `10.1038/s41380-025-02973-7`，其 Data availability 指向该项目。详见[本次元数据核对](ngdc-metadata-verification.md)。团队选择 AD/NC 的依据、个体级受试者标识和实际矩阵生成方法仍需确认。

## 2. 数据从哪里来，前端接在哪一段

```text
论文、公开数据项目、样本元信息
  → 明确本次纳入的测序样本及下载文件
  → 清洗得到 Clean Reads
      ├─ Reads 分类与丰度估计 → 样本 × 物种
      └─ 组装得到 Contigs
          ├─ 基因预测、功能注释、Reads 定量 → 样本 × KO
          └─ 分箱、优化、质量评价、去冗余 → 代表 MAG 集合
              ├─ 分类 → MAG 分类表
              ├─ 构树 → 系统发育树
              ├─ Reads 定量 → 样本 × MAG
              └─ 基因预测、功能与特殊功能注释 → MAG 功能关联表

上游交付：数据表/树文件 + 样本清单 + 生成说明 + 文件版本
  → 平台校验、登记版本、入库及计算
  → 前端查询、比较、可视化、下载与来源说明
```

上述路径来自流程文档，不能替代本批数据实际运行命令。2026-10-01 已收到历史脚本归档和软件版本清单，详见[脚本与版本核对](bioinformatics-script-provenance.md)。归档可读到组装、分箱、质量筛选和 dRep 参数，但最终服务器脚本、成功日志及物种/群落 KO 的生成方法仍未完整交付。

同日进一步收到服务器转交文件，CoverM 脚本、成功日志与 MAG v3 来源已对上，CheckM2 和 GTDB-Tk 成功证据也已补齐；当前物种 Excel 与本批服务器物种表的特征/数值尚未对上。最新详情和缺项见[服务器转交核对](server-transfer-audit.md)。

## 3. 每份数据有什么用

| 数据产品 | 最基本的含义 | 前端可以支持的问题 | 当前交付情况 |
| --- | --- | --- | --- |
| 样本元信息 | 样本编号、分组、年龄、性别、批次等 | 这批数据包含谁？当前筛选后还剩谁？ | 已核对 185 个样本的 Run/Experiment/BioSample/别名、分组、年龄和性别；匿名受试者 ID 待补 |
| 样本 × 物种 | 每个样本中各物种的丰度 | 组成、组间分布、差异、样本结构 | 当前使用 185 × 9,819；当前源表仅含 AD/NC 185 个样本 |
| 样本 × KO | 每个样本中各 KO 的群落功能丰度 | 功能分布、组间差异、样本结构；通路解释还需可靠 KO 映射 | 当前 185 × 2,258；丰度单位及标准化方式待确认 |
| 样本 × MAG | 每个样本中各代表 MAG 的丰度 | MAG 分布、热图、组间比较 | 已接入 185 × 872，CoverM 相对丰度单位为 % |
| MAG 分类 | 每个 MAG 属于哪个分类层级 | 分类组成、分类筛选、MAG 详情 | 已接入 872 个代表 MAG 的 GTDB 分类 |
| MAG 质量 | 每个 MAG 的完整度、污染度等 | 质量散点图、质量详情 | 已接入 872 个代表 MAG 的 CheckM2 质量 |
| MAG 去冗余关系 | 哪些成员对应哪个代表 MAG，成员来源及实际 ANI | 聚类详情、成员追溯 | 已接入 8,548 个成员与 872 个代表的关系 |
| 物种分类对应表 | Reads 分类标识与 MAG 分类标识的对应状态 | 查看可对应、未观察到及未解析的分类 | 已接入；不是具体 Reads 比对到 MAG 的证明 |
| 系统发育树 | MAG 之间推断的进化关系 | 树形展示，并关联分类、质量、丰度等外圈信息 | 已收到含 869 个细菌 MAG 的 GTDB 分类定位 backbone 树；独立 IQ-TREE 结果及古菌对应树未交付 |
| MAG × KO / 基因功能注释 | 每个 MAG 的基因携带哪些功能 | MAG 功能详情、功能分布及可追溯的归属解释 | 待完成：MAG 功能注释仍在进行，完成后交付 |

分类层级树按门、纲、目、科、属、种组织节点；系统发育树来自序列及构树分析。当前分类数据不能代替系统发育树文件。

样本 × KO 是整个群落的功能丰度，不能直接作为某个 MAG 的功能。功能注释和功能丰度也不同：携带哪些功能与这些功能在样本中的定量需要分别说明。

## 6. 生信交付与前端开发怎样分工

生信成员负责提供实际数据产品及生成事实；数据接入层负责校验、关联、版本登记和计算；前端负责把这些数据转化为可理解、可比较、可追溯的分析界面。具体负责人可以由团队安排。

对前端开发，每个新模块先明确六件事：

1. 数据回答什么问题，例如组成、组间变化、质量或进化关系。
2. 一行/一列是什么，主键是什么，能够关联哪份数据。
3. 数值单位是什么，能否比较或汇总。
4. 本次实际覆盖哪些样本、MAG 和分组。
5. 图表会计算什么，哪些只是展示筛选。
6. 来源、生成说明、版本和下载入口在哪里展示。

已有物种、KO 和 MAG 模块可以继续开发。系统发育树与 MAG 功能模块应以真实结果文件为接入依据。

建议当前优先完善三个界面入口：

- **数据总览**：列出交付产品、实际维度、用途、版本，以及已接入/待完成/结果待交付/元信息待确认状态；分析进度与资料完整度分别记录。
- **来源与样本范围**：展示论文与项目标识、当前样本清单、纳入依据、分组及原始表与分析表的数量差异。
- **每个图的说明与溯源**：展示数据单位、当前分析范围、计算规则、输入版本和下载入口。

以上是开发建议，不代表这些入口已在本次实现。

## 7. 批量服务器运行前统一交付约定

每批结果至少交付：

- 一份样本清单：样本编号、分组、来源研究、可用元信息及纳入/排除依据。
- 一份生成说明：流程/工具/数据库版本、关键命令与参数、运行时间和输入版本。
- 各项真实产物：矩阵、分类、质量、树、功能关系表等，并说明主键、字段与单位。
- 一份文件清单：产物类型、相对路径、维度、文件 SHA-256、交付版本及生成它的运行编号。

系统发育树还需交付叶节点与 MAG ID 的对应关系、构树依据及支持度等说明；可使用 Newick 等格式，由实际构树工具输出决定。

MAG 功能注释优先保留 `MAG ID → Gene ID → 功能编号` 明细，并说明使用的数据库和评分规则。KO 是否存在、是否能汇总为 MAG × KO，以及数值表示存在/缺失还是基因数，均依赖实际结果，不能预先假定。

本次参考脚本明确区分第 13 步 DRAMMA 抗性基因预测和第 14 步 DRAM 代谢注释。“dramma”与参考脚本中的 DRAMMA 名称吻合。用户于 2026-10-01 确认 MAG 功能注释尚未做完，状态为待完成，正式结果与对应运行记录待分析完成后交付；具体子步骤的成功数量不预先认定。现有群落 Sample × KO 已交付，生成链路和单位等资料仍待说明，两者分别登记。
